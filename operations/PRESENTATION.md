# Presentation：证据感知的人机协作 PPT 制作

## 入口与成熟度

`presentation` 是当前工作上下文内按需组合的能力，不是新的持续工作类型。研究项目内制作汇报继续保持 `research`；接续已有项目时先读取对应 `notes/status.md`，再定位该 PPT 的创作记录。

```bash
python3 .scripts/route.py --capability presentation --capability-profile create
```

**当前阶段：1B 工程实现（真实用户三页验收与 PowerPoint 人工检查待完成）。** 阶段1A持久状态与单页闭环继续可用；现在支持按所选制作方式从有效快照组装整套 PPTX 与预览，并提供独立的 PPT形式检查、PPT证据核查、PPT引用脱敏入口。整套 PPTX 最终组装不自动触发这三项辅助动作。受管IR编译器只支持三个受限版式，另有独立的模板库实例化能力，两者尚未打通任意模板导入；三个版式不是设计方案的默认选项。只能经 validator/commit 写正式状态，不能手工改 JSON 伪造批准。工程测试通过不等于真实用户验收通过。

## 当前可执行动作

```bash
python3 .scripts/presentation_runtime.py doctor
python3 .scripts/presentation_runtime.py smoke
```

- `doctor`：检查当前 Python 的本地依赖与 LibreOffice 路径，输出 JSON，不创建创作文件。依赖可导入不等于渲染已验证。
- `smoke`：只生成一页固定合成样例（中英文字、矩形、绑定端点的连接线），调用现有本地 PPTX→PDF→PNG 链路，回读原生对象和 PDF 文字，保存独立运行回执。它不是用户 PPT renderer，不接受材料、提示词或任意输出路径。
- Python 使用当前解释器。优先加载已安装的 `python-pptx`；缺失时从本机 bundled runtime 查找，或由受信任的本地环境变量 `PRESENTATION_PPTX_SITE` 显式指定 site-packages。其依赖加载后不长期改写 `sys.path`；不安装包、不修改 `.env`、不复制第三方字体。
- PyMuPDF、Pillow 和本地渲染仍使用现有 `visual_qa` 内核；LibreOffice 定位与 fontconfig 继承保持原契约。缺依赖、生成失败或回读不匹配均返回非零，不能自动调用远程 API。
- 每次 smoke 新建 `temp/presentation-runtime/<run-id>/`，不覆写历史；该缓存可删除，不是事实源。成功回执仅表示机械链路通过，`visual_review=not_checked`、`user_approval=not_requested`；字体报告区分请求字体与 PDF 实际字体，不宣称 PowerPoint 跨平台完全一致。

阶段1B 整套导出入口为 `.scripts/presentation_delivery.py export --store <store> --expected-revision <revision>`；先用 `presentation_state.py status` 读取当前 revision，逐页模式要求所有页已由用户接受预览并锁定；两种整套生成模式使用 `--mode auto|discuss-auto --instruction <真实生成指令>`，全部页构建和制作期视觉检查通过即可交付，回执注明待用户验收的页面。`presentation_delivery.py status --store <store>` 列出持久成品/报告及未提交目录。三个辅助入口分别为 capability profile `form-check`、`evidence-check`、`citation-redact`，仅用户触发时按需加载；导出不自动加载它们。完整命令与结果 schema 按需读取“阶段1B 导出与按需操作协议”。

阶段1A 入口为 `.scripts/presentation_state.py`：`example-plan` 给出协议样例，`init` 在已有 `projects/<workspace>` 建包，`prepare --kind content|design` 返回 `agent-task-v1`，`check/commit` 共用 validator，`status` 返回 revision、逐页快照和实际预览路径。具体命令/JSON 按需读取本文件“阶段1A 命令与数据协议”，不要猜测请求字段。

受管IR编译器只支持 `title`、`image_text`、`flow` 三个固定版式；图片是独立栅格素材，正文和普通框图使用原生对象。先按下节选择设计路径，再决定是否使用该编译器。每次批准绑定 `status` 的快照哈希和当前 revision；独立 API 检查实际预览后记录 `review`（新流程用 `review-api`），失败视觉审阅不能锁定；用户明确接受预览及原始警告后才能 `lock`。`build` 只接受空参数并调用本地 renderer，不接受手写“通过”回执。普通文字提纲仍按 `write`，旧图片/PDF重建保持独立。

## 模板发现与页面设计选择

三种制作方式及接续共用本节。Agent负责表达与审美判断，shared负责模板校验、实例化与既有事务；不增加自动语义评分、模板数量门槛或审批阶段。

**优化目标是高质量、高效率。** 质量包括内容准确与证据充分、叙事清晰与受众适配、视觉美观与可读性，以及可编辑、可接续的可靠交付；效率结合制作耗时、工具与模型成本、用户沟通和返工负担判断，不能仅以调用少或首次生成快衡量。优先复用合适资源与有效检查，避免无关检索和重复生成；不为速度牺牲必要质量。用户明确要求功能优化时，复用系统的工程工作项与日志，保存问题证据、原因、方案取舍、实施及验证结果，分别记录机械通过、用户反馈和实际质量/效率收益；正常制作不自动扩大为建设或增加评测调用。

1. **先定表达任务，再选实现。** 在既有提纲中说明各页要展示的关系、视觉焦点与图文分工，如方法对照、局域作用、过程或结果。主动考虑图文结合，判断哪些概念、操作或关系用图更容易理解，再按“图文结合与作图方式选择”确定图型和制作路径；文字用于点明问题、结论和读图线索。封面依下述标题页流程突出贡献；正文是否用纯文字由内容决定，不按固定比例分配布局。已有图形计划须实际兑现，变更时记录理由，不能无声改成条目列表。
2. **按页面类型检索模板库。** 首次设计或重新选版时运行 `python3 .scripts/wg.py slide-library search "方法 对比" --kind adaptable` 等用途查询；必要时换同义用途或去掉类型筛选，旧组件可能为unclassified。候选不足时，按主题、报告人、机构及来源类型，经query定位已摄入PPT，查看相关原页、相邻页及母版；“封面”等标签未命中不等于没有可用原页。找到能容纳本页内容的候选即可停止，不全库遍历或固定凑数。已知适用模板可直接show，沿用有效选择不逐页重复检索。按需加载 `route.py --capability slide-library --capability-profile general`。
3. **核验并真正实例化。** 对候选调用 `wg.py slide-library show --template <路径>`，比较用途、槽位容量、原生对象、来源与全稿风格。adaptable用 `use --template <路径> --values <JSON> --output <新单页目录>`，direct仅在原内容可直接复用时使用；unclassified先按库规范分类，不能冒充可填充模板。只读说明、仿照配色或看过缩略图不等于模板复用。保留实例回执、替换值及单页产物；新内容不继承模板中的科学结论或机构署名。
   已摄入公共域Raw原页可经 `wg.py slide-library extract --source <PPTX> --pages <页码> --output temp/<新目录> --name <名称>` 保留原生结构，再在项目副本中适配。记录原件/页码/哈希、提取包和实际改动；这属于原页提取复用，不冒充adaptable/use或正式受管导出，也不自动收藏进公共模板库。按内容调整原有文字框、留白、字号和配色，优先保留合适的背景、母版和图文关系，而非重新画一页仅借用颜色。
4. **保存简短选择依据。** 在项目现有设计笔记或逐页文件中记录“页/表达任务—候选及采用或不采用理由—实际路径—产物位置”。无合适模板时可原创；沿用配色、字号、页眉及图注层级，避免拼贴无关风格。图形可组合既有presentation-artwork/presentation-asset能力；程序不替Agent作审美决定。
5. **先检查代表页，再扩展同类页。** 整套模式先完成有代表性的封面、方法/概念页、结果页（按实际内容选取，不额外加页）的既有制作期API反馈，再扩展设计；无需新增用户确认。pagewise仍按原页序一次一页。结合文字反馈检查视觉焦点、信息层级、图的可辨识性和约定是否兑现；API passed、无溢出、模板来源可靠均不能代替这项判断。用户否定视觉效果后，将该版标为待重设计，不用机械通过覆盖反馈；不自动触发最终三项辅助检查。

**路径边界须在批量制作前说明。** 模板use只生成独立原生单页；当前 `presentation_delivery export` 从固定IR重建，不接受这些单页PPTX，也不保证保留模板外观。不要先实例化后又把内容抄回title并声称复用了模板。固定IR能充分表达时显式选用；不能时保留原生单页与来源，在已有可用工具范围内制作并如实标明独立草稿/汇总能力。没有经验证的整套路径时提前说明具体缺口，继续可独立完成的设计，不伪造受管导出，也不未经授权扩建渲染器。项目单页入口采用库规范支持的 `drafts/` 目录；正式哈希资产与revision保持不可变，用路径清单关联，不手改状态。

## 创作边界

- **用户主导最终检查**：PPT形式检查、PPT引用脱敏仅用户明确指令触发；可以提醒，不自动执行。PPT证据核查仅用户对具体内容有疑问时按范围执行。三项独立、默认不执行，均不作为默认交付门禁；详细约定见“按需辅助检查”。制作阶段按所选方式安排用户参与，保留机械校验、来源记录和隐私边界。
- 宿主 Agent 理解用途、检索证据、组织叙事、提出设计并与用户交互；视觉工作交给独立 API 提供制作期版式反馈，宿主结合科学含义、结构检查及实际预览作最终设计判断。shared 程序负责 schema、状态、几何、生成、机械检查和事务，不转交 DSH 控制循环。
- 需要语义暂存产物时，沿用 `agent-task-v1` 的 inputs/outputs/protocol/issues/check/commit/resume，不增加 DSH、`llm_structured` 或模型型 planner/critic。内容与设计只经原 validator/commit 进入创作状态。
- Raw 是科学与机构事实的权威。Wiki 与 graph 只用于发现和到达；主张、数字、图分别保存来源 locator 与来源版本，不把“路径存在”当作“主张得到支持”。用户提供但未核验的材料标记 `user_provided`，不伪造 Raw 引用。阶段1A仅接受 user_provided/unresolved，不把文件存在或 hash 匹配自动认证为 raw_verified；保留来源记录不等于自动逐项核查。PPT证据核查仅在用户对具体内容有疑问时执行，不默认生成全套证据映射。
- 私有来源的敏感性沿素材、IR、预览、成品和回执继承。输出路径变化不解除限制；未来远程上传须独立、明确授权，发布版引用不得泄漏本地私有路径。创作包仍为 local_only；`--allow-remote` 仅授权当前选定视觉输入上传，不是公开发布或其他来源的许可，private 来源不经本入口上传；smoke 无用户来源。
- 正文和标题优先 native text；适合用文字、几何图形和连接线准确表达的图，优先使用 PPTX 原生可编辑对象，包括普通框图、流程图和简洁量子线路。复杂插画、纹理或科研原图等适合整体图片的内容可独立嵌入；表格和有明确源数据的受支持图表逐步原生化。API 主创与可编辑对象可以组合：API 生成构图和图元，程序转换为原生对象，导出后回读确认可编辑性。不从图像估读并重造数据，不默认整页图片化。
- 现有 `slide-library` 及图片/PDF 重建保持独立、不迁移、不重构。旧页整页拷贝与 IR 重建不是同一种能力；任意模板、现有 deck 无损编辑、动画、SmartArt、复杂公式和第二 renderer 不在首版承诺内。

### 既有模板适配与用户修订复盘

适用于行政汇报、学院建设等参考已有 PPT 制作的任务，也适用于其他模板复用。宿主在制作与用户修订学习中落实以下规则；这些规则不增加默认形式检查、远程 API、逐步审批或用户确认环节，也不扩展现有 renderer 的能力边界。

- **清理模板残留对象**：替换标题后，检查原标题占位符与新标题是否同时保留。原位替换或删除已无用途的空文字框、占位符，保持一个实际标题入口；有填充、边框或版式作用的图形分别判断，不能因无文字一并删除。
- **文字以所属容器为边界**：卡片、栏框、色带中的文字框按该容器的内容区设置，统一左右内边距与中心线，明确对齐方式。页面以内不等于容器以内；收窄文字框后同步处理换行与高度，不用缩字号掩盖容器不匹配。
- **分割线兼顾美观与清晰**：分割线用于帮助辨认内容分区，按背景、投影显示和页面层级选择足够清晰的颜色/不透明度与线宽，避免贴近背景的浅细线。颜色与报告色系协调，线宽克制，端点/长度依内容区对齐，与文字和图形保留间距；同类分割线在同页及相邻页保持一致。标题横线、内部区隔线与图中有科学含义的连接线分别设计，不能批量加粗或改色所有线条。已有清晰且获认可的页面可作为当前报告的样式基准；具体颜色和线宽不固化为所有模板默认。实际导出后核对线条可辨识、分区清楚且不抢正文焦点；结构/颜色参数通过不能替代用户审美或真实投影体验。
- **依据背景分配图文区域**：先确认背景主体、低纹理/纯色区和可读对比，再安排标题与署名。图片偏左时可把文字放到右侧留白区；“放右侧”不等于必须右对齐。相关文字共用对齐轴，标题可用更宽文字框和更大字号；单位等长信息按学校/院系等语义分行，避免先缩字。按实际画布、内容和投影需求选择尺寸，不从单页固化绝对坐标或字号。
- **接续用户落盘版本**：用户说已微调/保存时，先在目标项目定位文件，对照上次交付哈希和内容确认版本；保留用户文件及基线快照，再开展后续编辑。文件变化后，旧预览、字体检查及API回执只属于旧哈希；生成脚本也可能落后于用户文件。以用户文件为当前编辑基准，更新项目入口，后续直接编辑其副本或将真实改动回补作者源并验证保真，不从旧脚本覆盖回退。独立文件不伪造成受管revision；仅在用户明确接受时按原事务锁页。
- **先对应页面，再比较修订**：版本可能删页、重排，按标题、正文与原生对象匹配页面后比较。结合用户说明判断修改意图，用户明确指出的误操作不提炼为缺陷修复、偏好或制作规则。记录有意义的文字、几何、字号、对象增删；图片关系编号、空文本 run 与段落结束样式的等效转换、保存软件补写默认值等，不直接视为用户修改或偏好。无法机械确认的可见差别再按当前任务边界定向查看。
  比较可见文字时，同一段的连续run合并，段落、显式换行及字段分别保留；run拆分不等于换行。几何比较包括共用对齐轴及文本框宽度，不仅比较左上角。先报告确定改动，再归纳可迁移方法与本报告偏好，不替用户猜测每个细节的动机。
- **字体意图与实际显示分开**：记录标题、中文正文、普通英文和数学表达各自的用户约定；要求中英文一致时，原生文字的Latin、East Asian及适用的Complex Script字体槽一致，并核对继承样式，不能只改中文字体名。先检查运行环境字体可用性；声明字体、已安装字体、PDF实际字体和目标软件显示分别验证。缺字体时保留PPTX的用户指定字体，明确预览替代，不能声称已经看到指定字形。字体、字号和换行改变后检查当前页容纳量，不将某位用户的字体组合变为所有报告默认。图片内文字按原图保真边界处理。
- **普通英文与公式分角色排版**：先按语义区分普通英文（术语、方法名、引文等）与数学表达（独立公式、行内变量、图中数学标注），再按已确认的字体约定分别设置文字run。用户指定“英文黑体、公式数学体”时，普通英文用黑体，数学表达用实际可用的数学字体（如STIX或Cambria Math）；中文标题/正文沿用其独立约定。数学变量通常斜体，数字、运算符、标准函数名及语义要求正体的符号保持正体；上下标按数字、变量或说明性文字的含义设置，不将所有拉丁字符或整个混排文本框统一覆盖成黑体。优先复用已验证且满足可读性、编辑需求的公式实现；简单公式可用数学字体文字与原生上下标，复杂公式或用户明确要求时采用原生公式结构。用户选定文字方案后沿用，不为例行排版反复探查应用或转换格式；选用数学字体不等于已创建公式编辑器对象。继承用户最新修订，明确替代旧约定的范围；检查字体槽、字号/基线、字符完整性及实际渲染，重新评估文本框容纳量。具体字库选择记录在项目，其他用户或模板的明确要求优先，不把一位用户的组合硬编码到全部报告。
- **区分通用修正与本次取舍**：将重复展开、篇幅与主次问题用于改进内容组织，按本轮用途和已知时长安排主稿与专题展开。删页只证明本次成品的范围，不自动撤销用户此前明确要求的主题，也不形成以后固定删除或固定页数的规则。

## 局部素材按需制作与复用

制作或修改 PPT，需要箭头、循环、反馈等可复用局部图形时，按表达用途调用 `python3 .scripts/wg.py presentation-asset search "反馈 循环"`。合适的候选用 `show --asset <id或路径>` 查看参数、来源和预览，再用 `use` 导出或 `insert` 插入独立 PPT 副本。已有素材 ID 时可直接使用，不固定每页搜索；没有合适素材时按需创作，不为复用牺牲表达准确性。

首次使用加载 `python3 .scripts/route.py --capability presentation-asset --capability-profile general`。`artifact.presentation_asset` 已登记为 Agent 可调用能力；原生图形保持可编辑，按报告配色和尺寸实例化，保存素材版本与参数。一次设计中值得积累的通用图形，可在用户收藏或持续建库授权范围内调用 `collect`；不自动收集整份汇报或第三方标识。

换色时先用 `show` 查看 `color_parameters`，再用 `use/insert --color '角色=#RRGGBB'` 按需覆盖；可组合预设，显式颜色优先。新创素材按背景、主线、节点/波形、符号等语义角色参数化，便于跨报告适配。

整页版式继续使用 `slide-library`，局部素材使用 `presentation-asset`。新创图形走 generated，文档提取走受限 source-derived；具体范围见 [素材规范](PRESENTATION_ASSET.md)。插入只生成新副本，不更改已有锁页快照或批准记录；受管演示稿需按原修订流程接纳新版本。固定版式编译器暂不直接消费素材引用字段，任意 PPT 可通过独立 insert 入口组合。

## 单篇论文制作方式选择

三种制作方式是 `presentation` 功能中的协作选项，沿用当前工作上下文。用户希望围绕一篇指定论文制作 PPT 时，在内容规划开始前向用户说明以下三种方式，并请用户选择。已有明确选择时简短确认并沿用；接续同一报告时读取既有选择。

> 这篇论文的报告 PPT 可以用三种方式制作：
>
> 1. **全自动**：你提供论文和报告要求，我自动提炼亮点、安排故事线、设计并生成整套 PPTX，完成后交你查看。适合希望尽快拿到完整版本。
> 2. **先讨论思路，然后一键生成**：先共同确定报告重点、叙事结构和页面安排；你确认方案后，我连续完成整套 PPTX。适合希望把握方向，把具体制作交给我。
> 3. **先讨论思路，然后逐页生成**：先确定报告思路，再一次完成一页，你查看并确认后继续下一页。适合希望细致参与内容和视觉设计。
>
> 你希望采用哪一种？

使用宿主提供的选项交互，选项名称与上述三项一致。论文、受众、时长、语言等信息先从用户请求和项目记录读取，必要缺口与方式选择集中询问；已有信息直接沿用。用户尚未选择时可定位论文和整理来源，制作按明确选择启动。新的单篇论文任务采用本节选择流程；原有逐页任务继续执行已选方式。

### 方式的执行与接续

| 制作方式 | 内部标识 | 讨论与制作节奏 | 交付 |
|---|---|---|---|
| 全自动 | `auto` | Agent 自主完成论文理解、亮点提炼、提纲、页面内容与设计，连续生成整套；常规取舍由 Agent 完成，关键输入缺失时说明具体缺口 | 整套 PPTX，供用户最终查看 |
| 先讨论思路，然后一键生成 | `discuss-auto` | 先讨论受众、核心贡献、背景故事、引文与页序；用户确认方案并指示生成后，连续制作和汇总 | 整套 PPTX，供用户最终查看 |
| 先讨论思路，然后逐页生成 | `pagewise` | 先讨论方案，随后一步一页；每页完整制作并展示，用户确认后继续 | 当前单页；完成后按汇总指令交付整套 PPTX |

“一键生成”指用户启动后由当前宿主 Agent 连续完成整套制作与汇总；底层仍按页生成和校验。三种方式共享论文溯源、文献编号、科学表述、原生对象优先和制作期 API 视觉反馈规则，区别在于用户参与节奏。远程视觉调用沿用既有来源范围授权。

在项目创作简报中记录所选方式、用户原始指令、论文来源、受众/时长/语言、方案讨论状态、制作范围、当前进度和待办。恢复先读简报与现有创作状态；用户中途更换方式时更新记录，保留已生成页面及其实际验收状态。该简报描述协作方式，底层 revision/快照/批准记录仍经受管状态事务保存。

### 两种整套生成方式

- `auto` 的模式选择及完整报告要求构成整套制作授权；`discuss-auto` 在方案确认并收到生成指令后开始整套制作。宿主依次完成各页内容、设计、build 与制作期 API 视觉反馈，修复问题后连续推进。
- 内容/设计的实施授权如实引用用户所选方式和页面范围。用户对整套制作的授权与实际预览接受分别保存，整套生成按 `auto` / `discuss-auto` 导出，未由用户查看的页保留待验收状态。
- 交付整套 PPTX 时简短说明内容、重要假设和待用户查看事项。PPT形式检查、PPT引用脱敏仍由用户另行指令触发；PPT证据核查仍针对具体疑问。

## 逐页制作与确认纪律

**选择逐页模式后，一步一页：宿主一次完成当前页，用户只确认实际整页。** 全局提纲、页序、故事线及素材定位可以提前准备；制作按 `slide_order` 推进，用户接受当前页实际预览并锁定后，才进入下一页。内容、设计、生成和制作阶段 API 视觉审阅合并在同一轮工作内，不逐项询问。用户要求调整时直接修改当前页并再次展示。

逐页模式的交互流程：**完成当前页 → 展示实际页面与必要问题 → 用户确认整页 → 锁定并制作下一页**。仅用户明确要求分阶段参与时，才分别提出内容或设计问题；真正缺少影响本页的信息时只询问该缺口。

**三种方式的修订均落在子文件夹中的单页。** 每页的内容、图形源文件、单页 PPTX、预览和制作记录集中在对应页面子文件夹；修订先更新该页源文件并重新生成、检查该单页，按所选方式展示。正式创作包沿用受管 revision 与不可变快照；隔离试验可使用 `drafts/第NN页-主题/` 及其修订版本，保留可回退记录。完整报告由所选单页版本汇总；两种整套模式按既有整套授权组装，逐页模式按请求汇总。日常改页以单页文件为编辑入口。

逐页模式内部沿用现有状态事务：内容提交 → 内容实施授权记录 → 设计提交 → 设计实施授权记录 → build → review-api → 用户实际预览接受 → lock。用户要求“一步一页”构成宿主完成当前页内容和设计的授权；`approve-content`、`approve-design` 的 `confirmation_source` 如实记录这项授权和当前页范围。shared 校验字段、快照和页内前置条件，不评价人类确认语义，也不提供跨页调度门禁。

“开始制作”“继续”等流程指令按所选方式推进制作；实际预览接受须有用户查看后的明确反馈。全局方案确认与逐页预览接受是不同记录，API 通过也只表示制作期检查结果。两种整套模式通过专用导出路径交付，保持用户批准记录真实。

发现授权记录失实或超出范围时按受管提交与失效机制纠正，保留历史并说明结果。恢复逐页任务时读取简报、`status` 页序和批准快照，从当前未完成页接续。

本节保留用户2026-09-25“一步一页”的制作偏好；2026-09-30 增加三种方式选择后，逐页确认规则适用于 `pagewise`，整套方式按上一节执行。

## 学术论文报告的叙事与风格

适用于介绍研究论文、突出工作亮点的学术报告；由宿主 Agent 在内容规划时使用。`presentation/create` 加载本节，其他用途按需取舍。它是可复用的创作经验，不增加程序校验、批准节点或自动辅助检查。用户当前要求优先。

### 先理解论文思路，再组织报告

从论文制作 PPT，优先沿用论文本身的科学问题、动机、论证关系和方法切入点，再转化为适合口头报告的表达。三种制作方式均在确定提纲前执行；接续时复用已完成的阅读与来源定位，只补读新问题所需部分。

1. **读清原文的论证链。** 先读摘要、完整引言和结论，结合方法、关键结果与必要讨论核对“为何研究 → 已有工作与不足 → 本文思路 → 证据 → 意义及边界”。识别引言各段如何推进问题及关键引文的作用，避免只凭标题、摘要或通用报告结构先定故事线。全文已读时直接提炼，不要求重新通读。
2. **优先保留科学逻辑，按受众转换页序。** 以原论文论证链作为提纲首选，按听众背景和时长压缩、展开、合并或调整呈现顺序；不机械照搬章节或逐段做一页。在思路讨论阶段，根据实际内容确定重要科学问题在哪里引出、需要哪些前置认识，可由一页提出，也可跨几页逐步建立，并在提纲记录各页作用；不固定页码，也不强制同一背景顺序。全自动模式由宿主在内容规划时完成同样判断，不额外增加讨论审批。已有通用故事框架和模板用于帮助表达，不能替代原文思路。确需改变主线、补充物理类比或引入外部背景时，在现有提纲中简记理由、原文章节/页码与补充来源，区分作者原意和报告者的解释。原文证据不足的主张仍须限定，遵从思路不等于认可所有主张。
3. **让引文服务这条论证链。** 从引言及相关章节的参考文献中筛选支撑当前页面的必要来源，优先到知识库定位并回溯 Raw；额外代表作按具体解释或比较需要补充。知识库缺少所需关键引文时，按下节“关键文献缺口与摄入接续”集中提出摄入建议，说明它支撑哪一步论证。无需收齐全部参考文献，也不因普通扩展背景缺失停止制作。
4. **在原提纲中保存取舍并接续。** 用简短主线、页职责和来源定位保留原文到报告的关系，无需另建逐段映射表。讨论后调整时同步版本与时间预算，按已选制作方式继续；不重复确认已确定偏好，也不把论文阅读、摄入或生成授权记成页面预览接受。

### 已明确的创作偏好

- **交付与简报直接表达目标**：默认交付可编辑的 PPTX。任务简报围绕目标产物、内容、风格及验收要求组织，用正向、直接、可执行的语句说明要完成什么。
- **页眉保持简洁**：顶部只保留必要的章节名称，默认不显示“1/3”“2/3”等章节内进度式页码。整份报告的底部页码可按需保留。本偏好来自用户2026-09-26对第二页的明确反馈，后续页面沿用。
- **用背景建立动机与重要性**：学术报告以清楚、有力地传播工作及其科学价值为目标。从论文引言及关键引文出发，说明问题影响什么、为何重要、已有思路解决了什么，再引出本文切入点。把核心问题的重要性落实到科学认识或实际需求，而不只加“重要”“重大”等形容词；专业同行也需要这一动机，深度按受众调整。
- **用具体推进呈现创新**：按当前问题介绍已有方法的操作对象、主要思路及适用的控制量，承认已有基础，再在共同对象和口径上说明本文改变了什么结构、假设、计算方式或研究路径，以及证据支持的意义。让前人思路、科学问题和本文选择自然衔接；创新依靠可核验的区别体现，不能仅靠方法标签或笼统贬低前人。结尾回应开场问题。
- **让重要文献进入页面论证**：对应页面显示可读的作者、期刊与年份等短引文，并在讲解中说明其作用。支撑核心动机或创新对照的引用进入屏幕内容，不能仅留在讲者备注或末尾清单。
- **引文字号照顾实际阅读**：在空间允许时优先给短引文合理字号和足够对比，不因其位于页脚就默认缩成小字。根据画布、投影场景及正文层级决定大小；常见16:9学术页可先试16–18pt，再按实际内容与模板调整，这不是所有页面的硬阈值。优先利用空余宽度、调整页脚容器或分行，并将冗长书目精简为可识别的作者/期刊/年份或必要标识，完整信息保留备注；不能为放大字号删除必要出处或比较条件。信息过多时先取舍/重排，再考虑缩字。相关页面的引文保持一致字号、位置和颜色，封面等不同角色可单独适配。实际导出后确认可辨识、无截断、与正文及页码不碰撞；文字能塞进框或API通过不等于投影易读。
- **突出理论工作的操作意义**：提出新量、新框架或新判据时，解释其定义为何这样选择、关键证明建立了什么联系、能用于判断或解决什么问题。严格证明、数值支持与推广展望分别标清适用范围。

### 可调整的制作技巧

| 环节 | 做法 | 使用范围 |
|---|---|---|
| 开场故事 | 短篇论文报告可用2–3页依次回答“为何重要／为何困难／本文如何切入”，每页推动一个问题 | 是起点建议；按报告长度、受众和工作性质压缩或展开 |
| 文献选择 | 优先选与动机、概念来源、方法基础和创新对照直接相关的引文，每页通常1–2条 | 以论证需要和可读性决定数量；期刊声望或引用数量不能代替创新论证 |
| 亮点层级 | 给关键定理、核心图及其意义更多讲解时间；技术推导、优化细节和扩展例子按需移入备注或备用材料 | 不按论文各节长度平均分配时间 |
| 页面语言 | 标题用简短主题、问题或结论直接点题，构造页可用“方法名＋构造实例”；维数、对象及配置放副标题或正文 | 示例条件用“以……为例”限定，不把演示范围误写为全文范围；具体标题形式不固定 |
| 专业公式 | 结合受众和时长安排定义、必要符号/维数与可计算实例，图与公式对应作用对象；详细收缩或推导按需进入备注/备用 | 不只展示通式，也不为展示数学而堆满指标；优先复用已验证的可编辑实现 |
| 实例与收益 | 展示实际意义时优先选已核验的代表性应用尺寸；将原配置与演示假设分清，给同口径绝对量、单位及相对变化 | 玩具例子用于解释机制，不以其小规模绝对量代表应用价值；更换尺寸后联动重算局域阶数、矩阵形状、图中支持范围和结论；比率由精确值计算，展示值可合理取整 |
| 配图 | 优先使用最能支撑本页论点的论文原图或原生示意；同一图重复出现时明确新的讲解焦点 | 保留图例与适用条件，不从图片估读并重造数据；视觉交给既有独立API流程 |
| 时长 | 为每页设预算并求和，短报告可预留约10%的余量；扩充背景时同步合并重复页或压缩次要内容 | 预算须经试讲校准；先区分总时段是否包含问答，固定页数不代表固定时长 |
| 模板 | 先确定本页的表达任务，再选直接使用型或套用填充型模板 | 模板应服务内容；沿用模板时仍按其用途、替换槽与来源约束执行 |

### 文献编号规则

介绍单篇论文的学术报告，页面引用默认沿用该论文原文的参考文献编号，便于听众对照论文查找。这是用户2026-09-26确认的制作偏好。

- 不按文献在 PPT 中的出现顺序重新编号；只引用部分文献时允许编号不连续，例如同页出现 `[1]` 和 `[28]`。同一文献跨页重复引用时保持原编号。
- 页面采用“原编号 + 作者、期刊、年份等短引文”；制作时对照原论文参考文献表核对编号与书目信息的对应关系，不能仅凭印象填写。
- 补充原论文未收录的文献时，用作者—年份等方式单独注明，不冒用原论文编号，也不挤占或改动已有编号。

### 文献与创新的写作尺度

背景引用说明相关研究，创新性通过“已有方法如何处理问题 → 本文改变什么 → 结果支持什么意义”展开。页面明确区分领域相关研究与本团队前期工作，按真实归属命名。比较代表方法时，先核对它们的操作对象、构造思路和约束，再选择准确覆盖这些方法的概括；方法有差异时并列概括或拆开说明，不为制造鲜明对比硬归为一类。本文特点优先落到具体结构、假设或执行方式；构造出发点的区别不自动意味着数学类别互斥或全领域首次。

论文引言及参考文献表可用于定位候选；书目核对与独立原文阅读是不同状态。涉及关键对比、具体定理、资源界或“首次”等主张时，定向阅读相关原文；尚未读到时收窄表述并在创作备注中保留阅读状态。不要把作者自己的概括当成已完成的独立优先权核验。页面优先清楚呈现有依据的区别，影响判断的条件就近说明，次要辨析放讲稿，保持表达力度与准确性。

对“打破”“突破”等有依据的强表述，先明确其指向的规律、基准或行为，以及图中可观察的变化，再校准标题与核心句；以精准对象保持表达力度。行为偏离、拟合参数变化和函数形式失效不是同一结论。可比模型、实测范围、训练来源或预算差异中会改变结论理解的条件应在页面可见，其余辨析留备注；口头解释不能补救页面错误或无依据的普适主张。证据不足则缩小主张，不机械弱化所有强词，也不把某报告的“打破”推广为默认措辞。

准备内容所需的文献阅读与来源记录仍按现有写作契约执行，不自动触发“PPT证据核查”或生成全套证据映射。“PPT形式检查”“PPT引用脱敏”仍仅用户明确指令触发；“PPT证据核查”仍仅针对用户的具体疑问。

### 核心文献、原图与影响力证据

按页面论点选取不可替代的核心文献，让听众看得出“哪项主张或哪幅图由哪篇工作支撑”。同一来源的题名、图注和页脚协调标识、合并冗余书目信息；多篇各有必要时就近对应，不以堆砌引用替代论证。短引文沿上述编号规则，完整定位留备注。普通制作中的对应说明不等于默认运行全套证据核查。

介绍经典实验规律时，优先考虑能直接展示其证据的重要原图，而非只列题名或公式。保留坐标、图例、拟合含义及必要条件，增加面向听众的读图提示，突出与后文有关的子图。解析图缺轴标或图例时回到原PDF选取完整裁区，记录来源页/图号及裁区；原始数据、重绘示意分别标明，不把不同数据集或测评口径的绝对值直接并为性能比较。

文献影响力确实有助于解释研究重要性，或用户明确要求时，再有界核验引用量、可靠奖项等证据。先用题名、作者、年份和DOI/arXiv等确认论文身份；优先复用现有核验，出现版本冲突、口径变化或需要更新时再查询。选一个足够有用的指标即可：引用量可用易读约数，页面同时给数据库与查询日期，备注保留精确数、来源链接和口径；不同数据库的次数不相加或互换。奖项核对颁奖机构及具体获奖对象，未核实就不采用，作者或其他论文获奖不归给本篇。影响力证据说明传播范围，科学重要性仍由问题、结果及后续影响解释，不以被引量证明正确性或创新。此判断不增每页必查任务或默认远程调用。

### 关键文献缺口与摄入接续

三种制作方式共用本约定，从讨论和内容规划开始执行，修改或跨会话接续时沿用已有记录。宿主 Agent 判断文献必要性及论证支持；shared 复用既有检索、摄入事务与来源校验，不增加 API 控制循环、模型审核或自动摄入。

1. **按论证需求查库。** 为核心动机、方法基础、创新对比和关键结果定位必要原文，说明该文献支撑的具体判断或页面。优先以原论文相关引文的标题、作者、DOI/arXiv等身份在知识库定位，核对版本和引用语境；按需要补充原参考文献之外的工作。已有可用 Raw locator 直接回溯；需发现时按 `query` 的 start/evidence/continue/answer 约定检索。论文参考文献表、Wiki摘要和图导航只提供线索，不替代关键主张的原文依据。分别记录未检索、已查范围内未命中、已定位但正文不可用、已读但支持不足；一次关键词未命中不能证明全库不存在。普通背景或仅扩展阅读的引用不自动升级为关键文献。
2. **关键缺口主动提示摄入。** 已查范围内未找到关键来源或原文不可用时，列出文献题目、作者/年份或 DOI/arXiv 等可确认身份、可用链接、所支撑的判断、关键性理由及已查范围，明确建议摄入或受管补齐原文。尚无具体文献候选时先说明需要何种证据并继续有界发现，不编造论文。当前已知需求合并提示，后续实质新增缺口再增量提示；文献身份、用途和用户决定均未变时不重复询问。
3. **复用授权，调用受管入口。** 已有授权覆盖当前来源和范围时直接沿用，否则请求本批关键文献的摄入授权。报告制作授权不自动包含写库授权。摄入按既有 ingest 参数、首次上下文预热及受管事务执行，Raw/Wiki/图不经手工写入。来源已存在但解析或定位损坏时按现有恢复入口处理，不为同一问题反复新建来源。
4. **在原工作上下文保留接续位置。** 在现有创作简报中维护“文献需求”小节，较多时另存 `notes/literature-needs.md` 并从 `notes/status.md` 链接。每项保留文献身份、用途/页面、关键性理由、已查范围及来源 locator、阅读与支持结论、真实用户决定及授权范围、摄入结果和下一步；未知项如实留待核验，不引入固定 JSON schema 或新的审批状态。记录是派生工作数据，正式页面修订仍走原内容/设计事务。
5. **摄入后回溯并接续。** 用户告知摄入完成或受管事务返回成功后，先读取项目状态与文献需求，核对实际来源、版本及 Raw locator，再读取相关原文并判断是否支持原问题。只有证据覆盖后才更新相关内容和下一步；入库成功不等于已读或论证充分。保留制作方式、提纲版本、原讨论位置与实际预览接受状态，不重新询问未变化的要求，不将本次摄入记成方案或页面已获批准。
6. **按证据依赖限定暂停范围。** 关键证据未取得时暂停依赖它的结论定稿，其他独立内容继续。普通背景缺失不阻断整份报告。用户暂不摄入时，可使用已取得且可追溯的外部原文、缩小或删除对应主张，并记录选择与来源状态；外部原文已足够支持时，建议入库本身不成为制作门禁。用户提供或外部阅读材料保持其真实来源标识，不伪造 `raw_verified`。

本流程属于创作所需的文献准备，不自动触发“PPT证据核查”，也不默认核查或摄入全部参考文献。恢复时优先读取已有需求和真实处理结果；只在来源、用途、用户决定或证据状态变化时补查和更新。

### 图文结合与作图方式选择

在思路规划和逐页设计时主动考虑图文结合：先明确图要帮助听众理解哪个概念、操作、结构或证据，再选择表达形式与制作方式。图负责呈现关系或变化，文字负责指出核心问题、结论和必要标注；两者就近对应，避免把整段文字重复画进框中或仅用装饰填空。简短文字或公式已能清楚表达时可直接使用，不设每页配图数量或图文比例。

| 表达需要 | 优先考虑的图形 |
|---|---|
| 抽象概念、局域作用、变换前后及方法差别 | 示意图、结构图或对照图，把关键变化画出来 |
| 模块组成、信息流、计算步骤与因果关系 | 框图或流程图，明确框的含义和连线方向 |
| 实验结果、已有方法的原始证据 | 可读的论文原图、数据图或已核验素材，保留坐标、图例和条件 |

图型与工具分别选择。先复用合适的论文图件、slide library、已摄入PPT或素材库；规则明确、需要编辑的示意图和框图优先采用原生对象。需要更丰富的视觉隐喻或构图时，可考虑API作图LLM主导，沿下文“图片创作方式”提交科学关系、来源、允许表达和风格约束，由其生成构图/图元后整合到PPT。已有模式选择和授权继续有效，范围内直接调用；新远程范围仍沿原授权与公开输入契约处理，不因每页选图重复询问。本条不新增API，也不默认每页调用模型。

同页和相邻页的配色、符号、线宽、文字层级与图注保持一致。连接线先按用途区分：流程箭头突出方向与先后，科学连线保持含义；同用途箭头的粗细和箭头头部协调，结合投影尺寸判断清晰度，不强求所有用途同一线宽。圆圈等容器内的符号按实际字形视觉居中，整组移动时同步核对。示意操作和实测结果明确区分，不凭空生成数据曲线或科学结论。作图与独立视觉审阅分开，回读实际导出的图文关系、文字可辨识性和可编辑性；在已有设计记录中简记图的用途、来源/制作路径及必要限制即可，不另建审批表。

### 减少重复返工的页内工作法

以下为宿主 Agent 的制作方法，来自2026年PRL报告逐页创作及用户反馈；不新增审批步骤、自动辅助检查或程序门禁。

1. **先确定每页的叙事职责。** 在现有提纲中用一句话注明本页回答什么、承接哪页、为下一页留下什么，并选定一个主职责：建立动机、解释已有思路、提出科学问题、介绍方法、呈现结果或收束意义。这些是职责选项，不是固定页序；同一重要科学问题可跨多页递进，不要求一页讲完。图表和文字围绕该职责取舍；背景页把主要空间用于重要性与切入点，完整方法综述、复杂实验解读和协议讨论按需拆开或移备用。经典背景与本文结果争夺焦点时，按理解依赖拆页：前页说明已知规律及其重要性，后页回答本文带来什么变化；不是每个主题固定拆两页。结果段优先呈现足以理解的核心发现，再安排解释性细节；初始化、恢复训练与测评协议按自身职责命名，比较条件清楚不等于性能结果。已有页面能够承载同一结论时合并，重复用图需明确新增问题或证据。由宿主结合已知目标决定，不增加逐项询问。调整页序后同步提纲、页码、当前版本映射及讲解稿，重新求和时长，不沿用旧版总时长标签。
2. **把用户反馈变为当前报告的默认输入。** 从现有提纲、状态和当前版本读取适用的术语、文献编号、字体角色、视觉层级和图形创作方式，将反馈背后的目的用于后续相关页；只有记录不足或冲突时补读历史，不逐页重读完整日志或重查已选模板。修改已有页的范围仍按用户指令。区分通用偏好、报告内约定、某页科学结论，避免把“本页去掉某词”泛化成所有论文的写作禁令。专业措辞修正除记录新词，还记录适用对象与理由。
3. **先校准结论与信息层级，再制作。** 对关键句明确对象、条件、证据等级和操作意义，按理解依赖安排视觉主位：统领全页的问题或结论通常靠上；构造实例页可先在上部讲清对象与构造，在下部用醒目的数值收束收益。位置服务阅读顺序，不把“核心信息靠上”或“收益放下方”当成固定规则。影响结论理解的定义、比较口径或成立条件就在相应内容旁简明呈现；次要计量提醒、实现细节与完整协议放讲者备注、相关结果页或备用材料。准确性与突出意义同时成立，不让预防性说明占据背景主位，也不为宣传删除必要条件。单层严格等价、数值支持与推广展望分别表达。专业术语在首次用于推理前给出足够定义；描述漂移、突变等现象时点明变化的对象、发生条件及所在区间，让文字与图中证据对应。面向用户仍一步交付整页，不增加单独的结论确认；该过程不等于自动运行PPT证据核查。
4. **按表达任务选择视觉形式。** 依据“图文结合与作图方式选择”，让图展示关系、文字指出重点。面向专业听众，用其熟悉的概念解释新方法的对象、控制量和结构；排序先交代基本对象，再展开作用关系，并核对对应是严格等价、结构借鉴还是直觉类比，在需要处说明。概念页考虑示意图，模块与步骤考虑框图，定理页突出对应对象及条件，结果页优先放大论文原图，创新页连接相关研究与本文推进。给创作 API 一个视觉焦点、已核对的科学关系与允许的图元；未提供数据时不让其补画带数据含义的曲线。使用原图时保留坐标、图例和裁区记录；密集内插图可单独放大或用原文数值及文字辅助，不能自行改动刻度或估读数据重绘。
5. **让实际导出约束提前进入设计。** 对密集编号和数学标注，给说明、编号、图形分别留出可辨识间距，编号与对象中心对齐，并按最长标签（如两位数）估计空间；先调整相邻区域再考虑缩字，关联图与公式同步移动。核对真实渲染中的间距和读图顺序，不以文本框未越界替代易读性。使用有余量的数学文本框，结合字体测量和实际PPTX渲染处理混排、上下标、换行与边框距离；避免把复杂公式拆成过紧的小字框。PPTAgent当前试验中的斜线旋转会产生方块，应使用已验证的水平/垂直连接和原生箭头，或验证其他连接线实现后再采用。页脚安全距离、中文图片路径等按实际转换器要求处理；这些兼容性约束不视作PPT普遍规律。
6. **分工审阅，交付前自主修正。** 宿主按Raw及图元文字核对科学意义，并连读标题、核心句、主图和收束语，判断本页主职责是否清楚、重要性是否具体、已有方法是否讲出思路、本文推进是否有依据、非核心说明是否挤占重点、与相邻页是否重复或脱节；按本页职责选取适用项即可。已有证据与偏好足以决定的问题在交付前直接修正，只有关键事实缺口或实质影响方向的未决取舍才向用户提问；不另增打分器、默认模型审核或确认阶段。独立视觉API读真实预览并反馈排版和可辨识性，其曲线颜色、门类型、DOI或科学结论猜测不直接覆盖来源。将缺字、重叠、裁切等可复现问题与纯审美偏好分别处理；已解释的符号不因模型建议就在每页重复长定义。API通过不等于叙事有效或用户接受，修改后的文件仍需绑定新预览与回执；逐页/整套节奏沿用户原选择。
7. **局部修订、保真合并、按影响范围检查。** 在当前文件副本上修改目标对象，避免从过期作者脚本重做整页。核对变更文字、字体、几何和实际渲染，检查范围覆盖受影响页；共享母版、字体或组装变化可能波及时再扩大。未改页以来源哈希、原生对象及必要渲染比较确认保真，可引用其原有检查，不把旧回执写成新版本已审阅，也不无理由重新调用整套视觉API。汇总时明确选取每页当前版本，记录文件与哈希，保留原生对象及图片依赖，核对页序、页数和内部关系。正式包经既有锁页与导出事务；隔离产物如实记录其状态。PPT形式检查、引用脱敏和证据核查按各自触发约定执行。

这些改进旨在减少重复提醒和实现缺陷造成的返工。研究重点、主张强度、受众适配及最终展示仍保留用户判断；本次认可的效果属于单个报告案例，不据此宣称模型、模板或自动化已普遍可靠。

### 总结与展望的收束

总结回到报告的核心科学问题，结合论文摘要与讨论，把方法贡献、代表性收益及科学意义连起来，给听众少量值得记住的结论。用有解释力的关键数字支撑收益，并就近保留模型/工作点、指标口径等必要范围；不再复制一遍实验目录、完整结果表或前页解说。具体列数与版式按贡献关系选择。展望优先依据原文讨论，明确区别已展示的结果和待探索方向；若倒数第二页已完成实质总结，末页可用致谢与论文信息收尾。

### 应用与经验来源

形成内容提案时，给出故事线、逐页表达任务、可见引文、拟用图件、讲解提示及时间分配，明确文献如何支撑动机与创新。修改提案时同步受管内容与页序，保留版本，不把讨论建议记成用户批准。

本节来自2026-09-24至28日PRL报告内容讨论、逐页制作及复盘。已明确的偏好是背景故事、创新意义和页面可见引文；技巧属于本次案例提炼的建议。中文页面配英文术语、专业同行受众，以及最初“12页／18分钟”的设定属于当次计划，实际页稿变化后需重算，其他报告重新确定。用户已评价本版质量不错，逐页实际PPTX经API审阅；尚无实际演讲与跨设备PowerPoint验收记录，不作为科学事实源或普遍验证的模板。

## 第一页（标题页）制作流程

封面帮助听众认出主题，并记住这项工作的一个核心特点。先确定值得记住的内容，再选择能使它直观、美观的表达；主视觉可用原图、概念插图或原生示意，文字已足够时保持简洁。以下是宿主在当前页内完成的工作，不增加逐项审批；沿用户已选的逐页或整套方式交付。

1. **接续最新文件和真实身份信息。** 以用户明确指定的文件为基准，核对哈希、首页文字/对象、背景及母版，记录本次范围。在副本修改，保留用户已经调整的题名、报告人、单位、日期、校徽及其他页面。用户后来填写的日期优先于早先留空的约定；来源不明的身份信息才询问，不能用旧作者脚本或旧预览覆盖新文件。
2. **确定一个核心记忆点。** 从论文贡献和受众出发，用一句内部设计说明回答“听众看过封面应记住什么”。选择最能代表工作意义且有依据的对象、变化、机制或收益；记忆点不是必须印在封面的口号。题名忠实于原题及已确认译法，用户要求直译时沿用；不以泛化科技背景、无关设备或易画的小细节代替贡献，也不把封面变成方法或结果的缩略目录。
3. **先明确图的含义，再生成图。** 在已有创作简报或illustration brief中简记：哪些图形对应哪些对象，位置/颜色/连接/箭头/运算符表达什么，哪些量和关系必须准确，哪些仅是概念性形象。先核对求和与连乘、并行与串行、相同与不同作用范围、输入输出和因果/关联；同形、同位置或移动对象都可能改变含义。以论文构造判断该同还是该异，不为构图好看机械错位或复制。例如局域项的不同支持域可用同一位置刻度上的不同作用块表达，但“三条链、左中右排列”不是通用模板。概念图不伪装成实测数据、真实设备、精确比例或已证因果。
4. **选择能承载主视觉的版式。** 沿前述模板发现流程复用slide library、已摄入PPT及已选素材；合适的封面继续使用，重设计时再查候选。把标题、主视觉、署名组织成清楚层级，预留图文空间，避免图中亮点与标题争抢注意力。图文左右、深浅底色、对比配色与占比均按内容选择。生成图时描述主体、对照关系、风格和留白方向；精确坐标、字号、节点位置与数学符号留到排版层控制。长单位按语义分行，校徽用原图保持比例；日期占位按用户要求。背景介绍、推导及制作说明进入备注，必要科学限定仍须可见。
5. **选择创作路径并保留可编辑层。** 下节分别说明素材复用/原生、API图元和API位图。用户明确要生图时采用可用的真实图片生成接口，在已有授权范围直接推进。位图负责形象、材质和复杂视觉；题名、署名、数学符号及精确关系标注优先用原生对象。需要不同作用位置或连接关系时，先保证科学结构，必要时将生成素材拆成可独立排布的图片对象与原生连线。照片、生成图和数据图的性质及来源如实记录，不能把裁切位图称为原生矢量图元。
6. **局部修订并判断是否足够。** 首张结果按简报检查：核心特点是否直观，科学关系是否正确，实际投影尺寸是否清楚，是否适合当前文字区。只有发现具体缺陷才迭代，不预设多候选或固定轮次。已有形象可用且只是位置、比例、留白或标签问题时，优先裁切、局部重排或原生覆盖标注；核对裁切、遮挡、节点与连接仍表达同一含义。整体图意不成立、素材无法局部修复或质感不合格时再改提示词重生成。生图误画坐标、乱码、额外结构时不直接接纳；简化提示或把准确部分移回可控层。达到表达与版式要求即交付，不仅为比较风格重复调用。
7. **检查实际整页并按原节奏交付。** 先回读文本、对象、几何和源文件差异，再用实际导出的整页预览完成既有制作期视觉反馈；局部图好看不代表放入标题、校徽后仍协调。宿主负责科学含义、证据范围和最终设计判断，结合独立视觉API的文字意见修正真实问题。对满版背景导致的边界提示等，核对对象位置和实际预览，保留原提示与处理理由，不为机械通过盲改用户内容。检查目标页及实际受影响部分，未改页复用保真证据；母版变化可能波及时才扩大。成品、新预览与版本记录对应，保留源文件和必要素材/来源，按用户要求将废弃中间产物移入回收站。制作完成、检查结论和用户接受分别记录，不自动新增最终三项辅助检查。

### 图片创作方式（Agent / API LLM 主导）

沿用用户已选择的模式和授权，不逐页重复询问。宿主先确定图意及科学约束，再选择输出媒介；“API作图”须说明实际产物是有限图元还是位图，不能用一个模型名混称两种能力。

| 路径 | 适用内容与实际产物 | 现有入口 |
|---|---|---|
| 素材复用与原生构图 | 原始数据图、已有封面、需要精确位置/连接或后续编辑的示意；文字和关系由宿主控制 | slide-library、presentation-asset及当前可用的原生编辑路径 |
| API主创有限图元 | API依据简报设计有界图形关系，返回`presentation-artwork-v1`；校验后导出SVG/原生HTML，不是图片生成端点 | `presentation_artwork.py generate --creator api --brief <json> --allow-remote` |
| API生成位图 | 复杂插图、材质与概念形象，返回PNG/JPEG；与原生文字/关系标注组合 | `illustration`的`raster`路径，复用`comic_generation.py`真实图片API |

**位图路径按需加载，不另建封面生成器。**

```bash
python3 .scripts/route.py --capability illustration --capability-profile general
python3 .scripts/comic_generation.py models
python3 .scripts/illustration.py prepare --output-root projects/<工作区>/outputs \
  --document report-cover --asset cover-v1 --medium poster --renderer raster --canvas 2560 1440
```

`outputs`须已存在；`poster`是现有接口的单幅版面语境，不改PPT交付类型。画布按实际版面与供应商能力确定，示例尺寸不是默认门槛。宿主按返回的`agent-task-v1`填写brief，复用`message/analogy/boundaries/style/placement/prompt/sources`，不新增一套封面状态或强制表格；随后执行原`check`，用`render --run <run> --model <目录模型> --dry-run`预检，再在已获授权下加`--allow-remote`真实生成。模型按当前配置、可用性与用户选择明确指定，不把某次成功的型号固化为所有封面默认。模型失败保存回执并说明原因，按既有规则处理，不静默换模型或把占位图当成生图成果。

位图提示词以简明自然语言说明主体、关系、风格及留白，给出少量必要约束；像素坐标、颜色代码、版式参数或长段禁令不应成为模型要画的内容。需要精确文字或关系时明确留给PPT层，少量概念标签也优先原生添加。仅发送选定且允许远程的绘图描述；来源locator不自动读取上传，不发送整份论文、私有信息或完整项目上下文。private按既有隔离入口执行。详细参数、路径、模型与回执边界见[插图规范](ILLUSTRATION.md)和[API绘图规范](COMIC_GENERATION.md)。

**有限图元路径沿原协议。** 不指定`--creator`时返回Agent任务；显式API模式由API根据科学约束和设计简报主创图元，不能把宿主预先完成的图交给API点评后称为API创作。当前`PRESENTATION_ARTWORK_MODEL=GLM-5.3-FlashX`通过chat/completions返回有限图元JSON；不是位图能力。候选、哈希和回执保留在`temp/presentation-artwork/<id>/`，按任务给出的validator/render接续，拒绝任意代码、越界及未知字段。宿主后续裁切或重排如实标为适配，不把最终构图全部归于API。

**检查与交付独立。** 作图与独立视觉审阅用途分开，即使模型相同也不混称；API意见不代替科学判断、用户验收或公开授权。原生对象导出后回读确认；图片和提示词留在项目可接续位置，素材选择、来源及有意义的失败原因进入现有制作记录，不新增逐轮长报告。三条创作路径均不扩展固定IR renderer的能力承诺，不绕过既有revision/锁页事务。

### 经验来源与适用范围

2026年PRL报告的标题页反馈形成“突出主要贡献、信息克制、明确图意”的原则；MixT报告2026-11-22的封面反馈补充“生图API与原生排版分工、图中位置承载科学意义、复用已生成素材局部修订、以用户最新文件接续”。案例说明这些判断需要前置，不证明所有封面都应配机制图或采用同一配色、节点数、模型和布局。

用户指导后的成品和API通过不等于自主初稿成功；实际投影、跨软件显示、减少人工干预和总成本收益分别观察。沿自然制作已有反馈与回执记录效果，不为证明规范而额外生成图片、打分或询问用户。历史PPTAgent等隔离工具试验保持其原适用边界，不冒称正式renderer已支持任意模板。

## 持久状态与权威（阶段1A已实现）

选定已有的 `projects/<workspace>` 一级工作区后，在其 `presentations/<presentation-id>/` 保存创作包。ID 随机且稳定；slide ID 与页序分离，不使用中心顺序号。

```text
presentations/<presentation-id>/
  current.json                 # 唯一已提交 revision 指针
  revisions/<revision-id>/
    session.json               # 整体设置、页序、批准/锁定快照及父 revision
    deck_plan.json             # brief、叙事线、各页任务与整体风格
    slides/<slide-id>/
      content.json             # 本页主张、文字、素材引用、证据、备注
      design.json              # 版式、强调方式及受约束参数，不复制事实正文
      ir.json                  # 编译后的对象、坐标和素材版本
      build.json               # 本地构建检查与实际依赖/字体指纹
    receipt.json               # 本次提交的操作者声明、变更及验证
  assets/<sha256>               # 原始素材字节快照，非 Raw 替代事实源
  assets/<sha256>.pptx|pdf|png  # 单页构建及批准预览字节快照
  .writer.lock                 # 本机进程锁文件，不删除/换 inode
  outputs/<build-id>/           # 不可变成品/衍生版本/报告，receipt + seal 绑定文件哈希
  requests/<request-id>/        # 持久用户指令、范围、问题及版本快照，候选结果仍暂存在 temp
```

当前通过受管 init/commit 创建 revision 和 assets；delivery 在同一个本机进程锁内向 outputs/requests 写完整临时目录，fsync 后原子发布。`.pending-*` 只报告，不自动恢复或按 mtime 提升；输出失败不改变 current.json。临时编辑与可重建渲染放 `temp/presentation/`，用户批准的预览及依赖随创作包保留；清除缓存不会丢失批准依据。assets 中的 PPTX 是单页快照，不要用 PowerPoint 原地覆盖；另存为新材料再处理。

- `current.json` 指向的不可变 revision 是页面制作状态的唯一权威；状态不能靠可编辑布尔字段、聊天记录或 temp 文件恢复。时间戳用于审计，不用于判定内容一致性。
- 工作区事项只记整体进度及创作包入口，不再复制逐页批准。`notes/status.md` 仍是 workspace 工具管理的投影，不手写第二套真理源。
- 写入先检查 schema、路径、素材哈希和 expected revision；单写者锁内校验并构建新 revision，完成后原子切换指针。失败时旧指针仍有效；未提交 revision 不作为成功。恢复遇到冲突、损坏或外部改写必须报告，不按文件 mtime 猜测最新状态。
- 多文件提交不靠“依次原子写每个 JSON”冒充事务。进程中断、并发旧 revision 提交、损坏 receipt 等都必须有回归测试。
- 成品是派生产物，不自动写入 Raw/Wiki/公共图；用户要求收录时再走受管摄入。外部 PowerPoint 修改后的文件视为新版本输入，不反向覆盖已批准 IR。

## 最小协议与批准（阶段1A核心已实现）

第一版使用创作协议族 `presentation-v1`；内部编译产物为 `presentation-ir-v1`，本地构建回执为 `presentation-build-v1`，不独立部署 IR 服务。下表描述责任，当前精确字段以本文件下一节和共享 validator 为准：

| 对象 | 最少字段与责任 |
|---|---|
| Session | schema、presentation_id、revision_id、parent_revision、approval_mode=strict、slide_order、source_policy=local_only、approval_records；持有唯一批准记录 |
| DeckPlan | 用途、受众、语言、时长、核心信息、叙事顺序、主题版本；每页稳定 ID、表达任务及时间预算 |
| SlideContent | slide_id、标题、正文、素材/证据地址和备注；阶段1A仅接受 user_provided/unresolved |
| SlideDesign | slide_id、layout_id/layout_version、image_source；theme 由 DeckPlan 持有并参与设计快照，不提供任意代码、XML 或命令 |
| SlideIR | slide_id、画布、稳定 object ID、受支持类型、bbox、文本/素材哈希、样式、连接端点、editability/fallback 原因 |
| BuildReceipt | 输入快照、依赖指纹、实际对象统计、渲染产物哈希、分层检查与最终批准引用；不持有第二份可变批准 |

全局方案按所选方式由 Agent 自主制定或与用户讨论。逐页模式交互为一步一页：宿主合并完成当前页内容与设计、编译/生成/机械检查、独立API审阅真实页图（宿主只消费文字结果），再由用户确认实际整页并锁定，随后进入下一页。内部内容/设计实施授权与用户预览接受分别记录；两种整套模式依生成授权连续完成全部页，再导出供用户查看，具体范围见“单篇论文制作方式选择”和“逐页制作与确认纪律”。

批准事件记录 `kind`、`actor`、用户确认来源说明、`expected_revision`、`approved_at` 与 `snapshot_sha256`。内容批准绑定内容与证据版本；设计批准再绑定布局、主题、素材及内容；成品批准再绑定 IR、renderer、实际字体/配置、预览和检查结果。使用规范化 JSON 与原始素材字节计算 SHA-256；状态检查不得只看 `approved: true`。

**信任边界**：hash 只能证明批准针对哪个快照，不能证明用户真的说过“同意”。宿主 Agent 负责如实转录显式确认，不能替用户签批；程序拒绝缺失确认来源或快照不符，但不声称有独立的人类身份认证。

| 变更 | 必须失效/拒绝的范围 |
|---|---|
| 内容或证据版本变化 | 内容批准及全部下游批准、IR、渲染、QA |
| 仅设计变化 | 保留内容批准；设计批准及下游失效 |
| 素材、theme、layout、renderer、字体/渲染配置变化 | 依赖这些版本的批准/构建失效；先给影响清单，不静默处理锁定页 |
| 修改其他独立页面 | 已锁定页面内容、设计、IR、素材和批准快照不变 |
| 页序/页码/总页数变化 | 全局输出批准失效；检查会改变的页码对象并显式重新确认受影响页 |
| locked 页普通修改、重建或整体美化 | 拒绝；仅用户显式解锁后进入新 revision，历史快照保留 |

状态使用少量事实与派生阶段，不维护互相矛盾的 `state`、`locked`、多个可改 approval 布尔值。validator 由上述快照关系推导 `content_review / design_review / build_ready / preview_review / locked`；损坏或过期则明确返回阻断原因。schema 拒绝未知版本/字段、重复 ID、悬空连接、非法几何、外部写路径；阶段1A没有整页栅格回退入口。

## 阶段1A 命令与数据协议

所有命令在仓库根执行。先选定**已有**一级项目，真实接续项目仍先读其 notes/status.md；不为测试向活跃项目写入伪批准。

```bash
python3 .scripts/presentation_state.py example-plan
# 将输出作为 plan.json 草稿，按真实用途调整；init 不代表用户确认内容
python3 .scripts/presentation_state.py init --project projects/<workspace> --plan <plan.json>
python3 .scripts/presentation_state.py status --store projects/<workspace>/presentations/<id>
python3 .scripts/presentation_state.py prepare --store projects/<workspace>/presentations/<id> --slide s1 --kind content
# 当前宿主填写 task 指定的 request.json；原 validator 先检查，再提交
python3 .scripts/presentation_state.py check --store <store> --request temp/presentation/<task>/request.json
python3 .scripts/presentation_state.py commit --store <store> --request temp/presentation/<task>/request.json
```

- JSON 拒绝未知字段、重复键和 NaN/Infinity。请求严格含 `schema: presentation-v1`、`expected_revision`、`op`、`slide_id`、`payload`；全局操作 slide_id=null。每次成功提交都产生新 revision，后续请求必须重新读取，不复用过期 expected_revision。
- `init` 的 plan：schema、purpose、audience、language、duration_minutes、key_message、theme、slides。theme 含 id/version/font/background/foreground/accent（颜色为6位RGB）；slides 是稳定 ID → {task,time_budget_seconds} 的对象。初始页序由输入顺序确定，随后由 session.slide_order 权威保存。当前不支持新增/删除页，修改目的/叙事请 set-plan；主题改动使设计下游失效，其他 brief 变动使相关内容下游失效。
- `set-content` 的 payload：schema、slide_id、title、body（1–6个字符串）、notes、sources。source 含 id/path/sha256/locator/evidence_status/sensitivity。path 是本仓库 Raw 或 projects 下显式材料的相对路径；拒绝符号链接、隐藏/配置文件、创作包自身和不支持类型；单文件不超过50 MiB。来源变更必须更新 hash 并重新批准；旧素材字节不覆盖。所有派生物继续 local_only，即使 sensitivity=public 也无自动上传能力。
- `set-design` 只在内容已批准后接受 payload：schema、slide_id、layout_id=title|image_text|flow、layout_version="1"、image_source。前两项为一般字段；image_source 在 image_text 中指向本页 PNG/JPEG/WebP source ID，其他版式必须 null。flow 需要2–4条 body，每条一个原生矩形，使用绑定两端的原生连接线。title 是标题与文本区，并非任意封面设计器。`prepare --kind design` 对新页给出空layout_id，须由Agent完成设计选择后填写；原validator拒绝未选择值，已有设计则原样返回供修订。任务protocol同时指向本文件“模板发现与页面设计选择”，不增加批准字段或自动模板判分。
- `approve-content`、`approve-design`、`lock`、`unlock` 的 payload：actor、confirmation_source、snapshot_sha256、accepted_warnings。确认来源必须如实说明用户当前哪条明确确认；快照从 status 对应 content/design/preview 取得。除 lock 外 accepted_warnings 通常是 []；lock 必须原样接受本次 build 的警告列表。unlock 也须明确用户确认，不能因想修改就自动解锁。
- `build` 的 payload 必须是 `{}`，只有内容和设计均获准且未锁定才运行。生成/转换失败时 current 不变。程序记录请求字体、PDF实际字体，以及 renderer/依赖/字体文件清单 hash；需要本机 fc-list，缺失/指纹改变时不得继续确认旧图。单页输出与实际预览放 assets，status 给出路径，不通过外部回执导入成功标记。
- `review` 保留旧宿主记录兼容；新视觉流程调用 `review-api --store <store> --slide <id> --expected-revision <rev> --allow-remote`，程序写入真实 API 回执：除 actor/confirmation_source/snapshot_sha256/accepted_warnings 外，含 verdict=passed|failed、findings（字符串数组）。failed 至少一条问题并阻断 lock；需要修复时回到设计/内容提交、重建和重审。API 回执与实际 PPTX/PNG、结构快照绑定，不能把机械 pass 转录为“已视觉审阅”；API 通过不产生用户确认。
- `reorder` 的 payload 是 {slide_order:[...]}；当前保守拒绝涉及任何 locked 页的全局主题/页序操作，先列出 affected locked slides，再由用户明确解锁。重排清除单页构建/视觉批准，内容/设计不自动重写。尚无页码对象与整套输出批准。
- `check` 与 `commit` 走相同 schema/批准前置校验；check 不渲染、不提交 revision、不摄入素材，不能预告实际构建一定成功。commit 返回 committed 和 issues，依赖复验以 status 为准；status=blocked 的 CLI 退出码非零。只影响单页的操作不隐式重建其他页面。
- 恢复依据 current.json → receipt hash → 全部 revision 文件 hash 与资产 hash，不按 mtime。进程中断可能留下 `.pending-*` 或未引用 revision，status 只报告 uncommitted_revisions，不把它们自动变成成功；current 已切换则读完整新 revision。坏 receipt/素材/外部改写应报告，保留现场并从可信备份恢复或作为新材料处理，不覆盖旧批准。
- 本实现使用本机 POSIX flock、fsync、原子 rename；**不是多台电脑/Synology同步副本之间的分布式锁**。同一创作包只在一个设备写入；同步冲突或存储介质不支持相同文件系统语义时先停写。发布/交付前仍需真实 PowerPoint 打开与编辑验收。

## 分层检查与最终交付（工程已实现，用户验收待完成）

1. 结构 lint：当前支持对象/引用有效性、越界、连接端点和字体范围，图片用 contain 保持比例。长文字仍可能溢出；PDF文字回读只是机械门禁，不代替查看图像。警告与确定性错误分开，不按 bbox 武断否定合理叠放。
2. 本地实际渲染：复用 PPTX→PDF→PNG。仅本地确定性检查通过不等于视觉审阅通过；未检查、失败、警告分别保留。
3. 独立 API 预览审阅：`review-api` 看实际图像后记录 verdict=passed|failed、findings 与 api_receipt；failed 必须说明问题且阻断 lock。审美建议与可见缺陷分开，不能静默修复锁定页。
4. 按所选方式交付：逐页模式由用户接受真实预览后锁页；整套模式生成完整版本供用户最终查看。严重结构错误和渲染失败不能通过用户批准绕过；可接受警告需明确记录，不改写原 QA verdict。

**阶段1B 整套导出已实现：** 最终 deck 从通过对应模式前置检查的内容/设计/构建快照生成，不拼接不受控单页二进制。默认保留生成所需的结构、文件完整性与页数/页序等机械校验，不自动逐页对比最终可见画面、全文核查证据或改写引用。最终检查以用户为主；交付可简短提醒用户自行查看，并说明可单独请求下列辅助功能。锁定绑定批准快照，不承诺 PPTX ZIP 或带元数据 PDF 的逐字节相等，也不把未经复核的整套成品称为已复核通过。

默认交付 PPTX、构建 receipt 与已生成的预览，明确三项按需检查未执行；证据映射不是必交附件。object counts 只能说明组成，不能用可编辑对象比例掩盖关键科学图不可编辑。跨平台 PowerPoint 打开、编辑与字体检查由用户进行，LibreOffice 检查不能代替它。发现的确定性错误仍须报告，不因检查可选而隐瞒。

## 按需辅助检查（独立入口已实现）

三项使用独立名称，可单独指定范围，不互相连带触发；中文名称是用户对话入口；CLI 使用独立 profile/kind：`form-check`、`evidence-check`、`citation-redact`。

| 独立名称 | 触发方式 | 执行范围与结果 |
|---|---|---|
| **PPT形式检查** | 仅用户明确要求时执行；交付时可提醒 | 对指定页或明确要求的整套成品，与制作期单页预览核对可见文字、布局、图片、字体及页序，检查遮挡与溢出，报告形式问题及预览差异；不检查事实依据，不自动修改或重新批准页面。例如：“做一次PPT形式检查，只查第3–5页。” |
| **PPT证据核查** | 仅用户对具体内容有疑问时执行；用户直接问出处或依据即构成触发，无需再说固定口令 | 追溯所疑问的主张、数字或图片，给出来源版本、具体位置及是否支持该表述；不扩大为全套逐项审计。例如：“第4页这个数字哪里来的，是否有依据？” |
| **PPT引用脱敏** | 仅用户明确要求时执行；准备对外分享时可提醒 | 按用户指定范围处理原生标题、正文和备注中引用的内部路径、私有标识等，生成独立衍生版本并保留原件；当前不改图片像素、不保证完整隐私审计；不连带触发形式检查或证据核查。例如：“只做PPT引用脱敏，其他不检查。” |

未请求的项目记为“未执行”，不写成 passed，也不以此阻止默认本地交付。用户说“制作/导出PPT”不等于授权三项辅助检查。制作阶段仍保留必要来源 locator、版本及未核验标记，不编造来源或认证；不执行引用脱敏不表示允许泄密或发布，私有来源仍保持 local_only，脱敏也不构成内容公开授权。检查中发现问题应报告；需要修改已锁页面时仍按显式解锁/重批流程处理。

## PPT形式检查入口

仅用户明确要求时加载 `presentation/form-check`；可以提醒，不自动做。将用户页码转换为指定 output 的稳定 slide ID，准备独立 `agent-task-v1`：

```bash
python3 .scripts/presentation_delivery.py prepare --store <store> --expected-revision <revision> --kind form-check --output-id <output-id> --slides s1 s2 --instruction '<用户的真实检查指令>'
```

当前 Agent 调用任务 refresh 命令（`form-api --result <result.json> --allow-remote`），由独立 API 同时接收实际成品 PNG 和对应制作期单页 PNG；宿主只读文字结果。仅检查请求页的排版、字体、图片、遮挡/溢出、页序与预览差异；不检查事实依据，不顺带脱敏，不替用户确认。按任务的 check/commit 提交逐页发现；详细结果 schema 按需读取“阶段1B 导出与按需操作协议”。API 未完成时返回 partial，不伪造通过；页面未批准的新衍生版本不能靠形式检查继承原预览批准。

## PPT证据核查入口

仅用户对具体内容提出疑问时加载 `presentation/evidence-check`；用户直接问出处即构成触发，不要求重复口令，不默认全量审计。无需先导出或锁定，页面已存在内容和来源即可：

```bash
python3 .scripts/presentation_delivery.py prepare --store <store> --expected-revision <revision> --kind evidence-check --slides s1 --instruction '<用户的真实提问>' --question '<具体疑问>'
```

当前 Agent 仅核查疑问范围，沿声明的来源回到原始材料，区分有出处和支持结论。程序只核对来源快照哈希、明确页/行位置及逐字引文，不判断逻辑支持，不把项目材料认证为 Raw。文本来源用 lines:N-M，PDF 用 page:N；扫描页/图片不能用文本引文证明时报告 insufficient 并说明需视觉核对或补充材料，不能编造引文。需要新来源时先走原内容更新/批准流程；不直接修改 Raw。结果按任务 check/commit 保存，详细 schema 见“阶段1B 导出与按需操作协议”。

## PPT引用脱敏入口

仅用户明确要求时加载 `presentation/citation-redact`；对外分享前可提醒，不自动做：

```bash
python3 .scripts/presentation_delivery.py prepare --store <store> --expected-revision <revision> --kind citation-redact --output-id <output-id> --slides s1 --instruction '<用户的真实脱敏指令>'
```

当前 Agent 在指定页原生文本引用槽位提出完整字段 before/after；程序验证目标范围与旧值，重新生成独立 PPTX/PDF/预览，不改变锁页或原件，不触发形式检查/证据核查，不继承用户批准。当前不处理图片像素、任意外部 PPTX、隐藏的第三方对象，也不保证清除了全部敏感信息。成品及内部回执仍为 local_only；回执/快照保留源上下文，不能将整个输出目录当公开包。脱敏不等于公开授权。详细 schema 按需读取“阶段1B 导出与按需操作协议”。

## 阶段1B 导出与按需操作协议

`export` 默认 `--mode pagewise`，保持已锁页导出契约；`auto` / `discuss-auto` 要求 `--instruction`，复验所有页已构建、制作期视觉 verdict=passed、来源与依赖一致。回执记录 `production_mode`、`generation_instruction`、`unaccepted_slides`；导出不修改单页批准记录或创作 revision。模式和授权的真实性由宿主依据对话判断。

`.scripts/presentation_delivery.py` 的提交和导出是 shared 确定性入口；`form-api` 显式调用独立视觉 adapter。当前宿主负责理解用户指令、消费文字检查报告、判断证据与提出引用替换，不能把 `--instruction` 存在当作已验证真实人类授权。

```bash
python3 .scripts/presentation_state.py status --store <store>
python3 .scripts/presentation_delivery.py export --store <store> --expected-revision <revision>
# 两种整套生成方式使用所选模式，记录用户实际生成授权
python3 .scripts/presentation_delivery.py export --store <store> --expected-revision <revision> --mode auto --instruction '<用户整套制作指令>'
python3 .scripts/presentation_delivery.py export --store <store> --expected-revision <revision> --mode discuss-auto --instruction '<方案确认及整套生成指令>'
python3 .scripts/presentation_delivery.py status --store <store>
# 仅用户指令/疑问触发后，用上面的独立 prepare；按 task 给定路径填写 result.json
python3 .scripts/presentation_delivery.py check --store <store> --result <result.json>
python3 .scripts/presentation_delivery.py commit --store <store> --result <result.json>
```

- **导出**：逐页模式要求所有页已锁定，整套模式要求所有页已构建且制作期视觉通过；来源版本及渲染依赖有效，从有效 content/design/IR 按 slide_order 原生组装，不读取单页二进制拼接。保存 PPTX、PDF、逐页 PNG、对象数/页数机械回执；不自动评判画面或逐项查证。`assistance` 的三个 kind 均为 not_executed，`user_approval=not_requested`。生成预览不是执行形式检查。
- **持久事务**：同一 Store 本机 flock；outputs/<id> 和 requests/<id> 均有 receipt.json 文件清单与 seal.json 回执哈希，完整写入后原子 rename，不覆盖已发布目录。读取核对文件集合与哈希，外部修改视为新输入而不是同步回写。check 不提交、不渲染；commit 再跑同一 validator。请求只能提交一次；状态/源版本变化必须重新 prepare。中断后看 status：完整输出保留，pending 不自动提升。哈希用于完整性，不是对抗拥有目录写权限者的签名认证。
- **prepare**：显式 kind、expected revision、非空且无重复 slides 和真实 instruction；form-check/citation-redact 必须指定 output-id；evidence-check 必须有 question，可不指定 output。请求范围与 base output 回执哈希持久保存；用户只要求导出不构成三项授权。候选结果位于 temp；删 temp 后可重新 prepare，但不可伪造旧结果已提交。
- **公共结果字段**：严格 `schema=presentation-assistance-v1`、request_id、intent_sha256、actor、summary、items。前三项由 prepare 给出，不改写；actor 为实际执行者声明（宿主或 API），summary 如实说明检查范围与限制。所有检查都不产生用户批准，执行状态 executed 不等于结论 passed。
- **形式 items**：每个请求 slide ID 恰好一项，字段 `slide_id, verdict, findings, inspected_preview_sha256, approved_preview_sha256`。verdict 为 passed/issues_found/unable_to_check；后两种必须有 findings 字符串列表。两个哈希分别取实际成品 PNG 与制作期单页 PNG；`approved_preview_sha256` 为兼容字段名，是否已被用户接受以批准记录为准，新 API 结果另含 `api_receipt`，程序核验 API 身份、源/页图/结构/批准图绑定和结果一致性；旧宿主格式保留历史兼容，不自动伪装成 API。只保存报告，不修改页面。
- **证据 items**：每个请求页至少一项，字段 `slide_id, claim, verdict, reason, evidence`。verdict 为 supports/contradicts/insufficient；前两种必须有 evidence。每条 evidence 严格含 `source_id, locator, quote`，source_id 必须在该页 sources 中；UTF-8 txt/md/csv 的 locator 为 lines:N-M，PDF 为 page:N，引文必须逐字出现在该范围。source hash/locator/逐字引文验证不是语义支持认证；报告保留宿主判断及未核验状态，不写 raw_verified。图片/扫描等当前不可做逐字校验时用 insufficient 明示限制。
- **脱敏 items**：零个或多个替换，每个严格含 `slide_id, field, before, after`；field 仅 title/notes/body:0…body:5，每页每字段最多一项。before 必须等于完整旧字段，after 为完整新字段并通过原 content validator。替换范围仅为指定页的文字引用，不接受任意代码、XML、路径写入或变更来源策略。items 为空表示未找到可处理文字引用，summary 必须如实说明；生成的独立版本也不冒充全面脱敏认证。
- **报告与隐私**：输出均保留真实请求、范围、版本和结果，不连带触发其他动作。脱敏衍生版本保留 origin snapshot 与原始引用上下文供本地追溯；内部 receipt、snapshot、context、result 不是公开附件。单设备写入边界不变，不声称 Synology 分布式锁。

## 学术报告摄入与模板结构复用

三个视觉模式共用 `.scripts/pptx_visual.py`：`content` 是摄入内容识读，`layout` 是设计与组件用途分析，`form-check` 是用户按需形式检查。主 Agent 不打开页图；纯文字语义 backend 保持不变。API 失败返回文字状态，不能回落宿主看图。缓存按原件、页图、结构、模式、模型与协议绑定；回执记录真实执行身份，不能认证人类批准或研究结论。

摄入按 INGEST「演示文稿（PPTX）」先做原生页面判别，仅图片或不可原生读取图形承载主要信息的页调用content API，结果以主题、图意和原页导航为目标。原生内容充分的页面记录无需视觉的理由，不逐页上传。页面判别和0至5个模板候选选择由同一Agent/API文字任务完成；原生结构和已有库帮助选择，不额外自动调用layout API。

```bash
# 只读结构提取，不联网；保存逐页字体/字号/布局/利用率/表格/图表/框图/示意图参数。
```

结构参数和视觉分析一起用于设计：精确值读取原生对象；视觉解释负责阅读顺序、层级与可读性。覆盖率是裁到画布后的对象包围盒并集估算，单独列出疑似背景排除项及含背景上界，不表示越高越好。声明/主题解析字体与实际渲染字体分开；图表缓存数据不重算，图像不可冒充可编辑表格或精确数据。

受管组件保存 component.pptx、component.md、structure.json、原版式分析回执和缩略图。复制保留所选原生页及其关系依赖；涉及未选页的跨页依赖拒绝提取，防止悄悄带入其他页。原始内容不自动通用化/脱敏；模板库复制与现有三个 IR 版式是独立能力，不承诺任意旧页自动套用。`reindex` 可恢复受管索引；正式收藏失败不撤销报告摄入。

摄入收藏按用途区分direct/adaptable，并使用明确的槽位profile。源绑定计划解释新增价值，shared核验profile、来源、选页及依赖，复用现有事务发布；精确重复只保留一份，近似版式由语义执行者判断。没有实际执行的视觉分析保留为not_executed；模板收藏不等于最终形式检查或用户批准。

### 直接使用型与套用填充型

两类按复用方式区分，同一来源页可以分别收藏：direct 保留原样内容，说明适用主题、来源引用、时效与使用限制；adaptable 保存替换位与容量规则，把指定文字和图片改为占位内容，用于填充新材料。旧库保留为 unclassified，不自动宣称可填充。

模板生命周期现归入独立功能 **PPT模板管理与复用**（`artifact.slide_library`），统一入口 `wg.py slide-library`，操作契约见 [SLIDE_LIBRARY.md](SLIDE_LIBRARY.md)。它可服务多个报告，持续创作上下文仍由项目工作区承载。

`.scripts/slide_library.py prepare-reuse` 消费已收藏组件及 Agent 明确编写的 `slide-reuse-v1` profile，生成 v2 候选；`collect` 仍按用户授权发布，去重加入类型与 profile 哈希。`search --kind direct|adaptable` 按类型检索。`fill --template <组件目录> --values <JSON> --output projects/<工作区>/drafts/<新单页目录>` 验证所有槽位后生成独立 PPTX、预览与来源回执，原件/模板不变。`show` 查看来源版本、用途与槽位容量；`use` 根据 direct/adaptable 类型创建实例。项目目标须为含 `workspace.yaml` 的工作区，项目输出限单页，新 `temp/` 目录仍用于临时实验。单页修改与确认后再进入整套组装；这不等于任意旧模板自动转成现有三个 IR 版式。

首版槽位限原生文字框和图片；文字保留对象几何、字体及段落样式，检查总字符/显式行数/单行字符预算；PNG/JPEG 等比居中留边。没有表格、原生图表或任意 SmartArt 自动换数据功能；其他对象必须明确声明固定。派生演讲备注改为模板使用提示，包内历史媒体/隐藏元数据不承诺全面清除。容量检查不等同于视觉通过，制作中的视觉判断调用独立 API，最终三项辅助检查仍遵循用户触发条件。

profile 和完整调用说明见 `slide-library/_rules.md` 第九节；具体模板的 `component.md` / `values.example.json` 提供替换指南，`structure.json` 保留精确参数。形式检验与 PowerPoint 人工编辑验收各自记录，不因程序成功而代填用户批准。
